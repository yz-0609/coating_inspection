## 本次交付

1. 从 ST 官方 `stm32f4xx-hal-driver/v1.8.2` 补齐 UART / IWDG 的 `.c/.h`，保留源文件原文和许可，启用 HAL 配置宏并更新 CMake。
2. 在 `Drivers/STM32F4xx_HAL_Driver/M0_VENDOR_MANIFEST.json` 记录来源、版本、长度和 SHA-256；已有 `stm32f4xx_hal.c` 版本同为 1.8.2。未替换其他依赖。
3. 建立 Bsp/Board、Bsp/Reset、Device、Module/Diagnostics、Application、tests 层次；Device 和 Application 当前只有实现边界说明。
4. GPIO 在切换输出模式前写入候选关闭电平，删除初始化后的补关灯操作；取消 PA1 EXTI 和无用途 PB3 输出。
5. 撤下 PC5 闪灯任务，使用原生 FreeRTOS 静态创建的 `M0Baseline` 任务和静态 Idle 任务。每 100 ms 更新 `g_baseline_cycles`，不操作结果灯。不再编译 CMSIS-RTOS 包装层。
6. 开启栈溢出检测、分配失败钩子及 `vTaskDelayUntil`。Error_Handler、CPU 故障处理与 RTOS 致命钩子尽可能关闭结果输出和 DE，然后停机。IWDG 尚未启动，因此本阶段不会自动从致命错误复位。
7. `main()` 第一项操作保存原始 RCC_CSR 和协议位掩码，然后清除复位标志；UART1 启动日志输出系统时钟、复位原因、原始 CSR 和候选接线确认标记。
8. 独立原生 GCC / CMake / CTest 工程和 VS Code 主机测试任务；M0 验证脚本检查依赖哈希与固件格式一致性。

更新了 `.ioc` 的候选 GPIO 默认电平和轮询输入；原生 RTOS、UART 仍由手工代码维护，不支持直接再生成覆盖。UART / IWDG 加入编译不表示已经实现 DMA、8E1、RS485 或喂狗。

## 上板验收操作与进入 M1 的条件

先确认以上表格、实际芯片及 25 MHz 晶振。输出关闭只由软件初始化保证到代码执行之后，复位期间引脚的物理状态需结合外部电路实测。

1. 连接实际调试器和目标电压参考，烧录、校验并复位，保存 OpenOCD 完整日志和 ELF/BIN 哈希。
2. USART1 接收启动日志：`sysclk=168000000`；记录 `reset` 和 `csr`。这是软件计算时钟，再用示波器或调试器检查实际时基，不能只凭日志确认晶振。
3. SWD 观察 `g_baseline_cycles` 每 100 ms 前进一次；检查 HAL_GetTick 与 RTOS tick 在连续运行中正常前进。记录观察时长及结果。
4. 示波器观察 PB2 / PC5 / PC2 / PB1，从上电、NRST 到调度开始，确认实际 PASS / FAIL 不出现错误亮起、DE 默认接收。
5. 分别上电、按 NRST 和执行调试器软件复位，观察 `BSP_ResetInfo()` 返回值和启动日志，多标志同时出现时全部保留。
6. 核对没有引脚复用冲突，完成接线表签认和测试记录后，把 `BOARD_WIRING_CONFIRMED` 更新为 1，再进入 M1。

本机设备枚举未发现名称匹配的 ST-Link、CMSIS-DAP、J-Link 或 USB 串口，仅发现蓝牙虚拟 COM11 / COM12；这不等于证明没有其他名称的硬件。未尝试通过蓝牙 COM 连接 MCU，未执行烧录。

## 已知问题与后续

- UART1 / UART2 为旧中断缓冲驱动，存在并发和满缓冲保护不足，仅用于本阶段启动信息与基础验证。USART2 在 M2 替换，USART1 在 M6 替换为有界非阻塞诊断。
- M0 没有工位状态和 FAULT 业务输出；全部候选输出保持关闭。不应接入生产流程使用。
- 内部致命错误在本阶段停机，M5 才启用条件喂狗及 IWDG 恢复。
- M1～M7 尚未实施，原因是用户计划要求逐阶段验收，M0 的实物接线、SWD、时钟、调度和复位灯态仍未满足进入条件。
